# Производство «Пропавшего Света»

> [!note] Решение
> Игра собирается в Unity как 2D immersive sim с боковой камерой. Основа производства — не попытка сразу реализовать семь дней и всю школу, а последовательное доказательство четырёх вещей: пространство поддерживает разные маршруты; персонажи живут по расписанию; свет является физической и социальной переменной; нормализация меняет поведение и речь без смерти NPC.

## Действующая ветка

- [[Архитектура игры]] — границы систем, OOP, данные и симуляция NPC.
- [[Графический pipeline]] — путь от скетча до рига, анимации и сцены Unity.
- [[Инструменты Unity]] — редакторские окна, импорт, валидация и сборка контента.
- [[Вертикальный срез]] — первая играбельная проверка всей формулы.

## Производственный принцип

> [!note] Решение
> Сначала строится маленький, но полный фрагмент игры. Он содержит один связный участок школы, урок, перемену и ночь; несколько NPC с настоящими маршрутами; переносимый ящик; разные способы пройти одну преграду; локальные источники света; разговор, подслушивание и одну необратимую нормализацию. Любая технология, которая не помогает этому фрагменту, не входит в основу проекта.

## Технологический набор

| Задача | Решение |
|---|---|
| Движок | Unity, стабильная LTS-ветка на момент начала реализации |
| Рендер | URP 2D Renderer, 2D Lights, Normal Maps выборочно |
| Камера | Строгая боковая проекция, Cinemachine только для переходов и кат-сцен |
| Персонажи | Unity 2D Animation: кости, Sprite Skin, Sprite Library, IK |
| Уникальные моменты | Покадровые клипы или сменные нарисованные позы поверх общего рига |
| Архитектура | Компонентное OOP с системами и данными; без Unity Entities/DOTS на старте |
| Контент | ScriptableObject для определений, сериализуемое состояние сохранения отдельно |
| Диалоги | Узловой граф/табличные данные с условиями; отрисовка текста собственным слоем |
| Навигация | Граф проходов и локальное движение в 2D, а не универсальный 3D NavMesh |
| Версии | Git + LFS для исходников графики и тяжёлых бинарных файлов |

## Главные ограничения

> [!note] Решение
> - Никакого постоянного HUD, кроме контекстной читаемости интерактивного предмета.
> - Никакого боя, здоровья и смерти игрока.
> - NPC используют те же двери, лестницы и направления движения, что [[Артимед]].
> - Каждый светлый участок имеет видимый или логически установленный источник.
> - Контент не кодируется внутри конкретной сцены, если правило повторяется в другой комнате.
> - Симуляция всей школы не означает одновременную отрисовку сотен полноценных персонажей.

## Критерий готовности системы

> [!note] Решение
> Система считается готовой не когда у неё есть классы и инспектор, а когда она создаёт проверяемый опыт игрока. Свет готов, когда по кадру можно принять решение без индикатора. Расписание готово, когда коридор ощутимо меняет функцию между уроком и переменой. Риг готов, когда один и тот же персонаж убедительно идёт в обе стороны, несёт ящик, скрывается и играет кат-сцену без распада фирменного рисунка.

## Порядок производства

1. Зафиксировать визуальный эталон персонажа и одного коридора.
2. Собрать графический импорт и один переиспользуемый риг.
3. Реализовать пространство, общие интерактивные свойства и сохранение состояния.
4. Добавить расписание и маршруты нескольких NPC.
5. Подключить свет, восприятие и скрытность без HUD.
6. Добавить разговор, подслушивание и типографическое состояние.
7. Собрать [[Вертикальный срез]].
8. Только после его проверки масштабировать школу, персонажей и дни.

## Что намеренно откладывается

> [!note] Решение
> Точные длительности, скорости, радиусы, количество батареек, веса и размеры подбираются внутри прототипа. База знаний фиксирует ощущение и причинность, а профиль баланса хранит рабочие значения отдельно. ECS/DOTS, процедурная генерация анимации нейросетью и симуляция каждого ученика на полном качестве не входят в обязательную основу.
