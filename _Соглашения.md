# Соглашения хранилища

Правила, по которым устроена эта база. Нарушать нельзя — иначе связи и реестры рассыплются.

## 1. Три уровня достоверности

Каждое утверждение в любой заметке принадлежит одному из трёх уровней. Их **нельзя смешивать в одном абзаце**.

| Уровень | Что это | Как оформляется |
|---|---|---|
| **Канон** | Прямо есть в повестях. Ломать нельзя | обычный текст + цитата-подтверждение |
| **Решение** | Принято для игры, канону не противоречит | блок `> [!note] Решение` |
| **Предложение** | Идея, ещё не утверждена | блок `> [!question] Предложение` |

Если факта нет в повестях и он не помечен — это ошибка заметки.

## 2. Именование файлов

- **Персонаж** — ровно имя: `Артимед.md`, `Мах.md`, `Данизавр.md`. Ссылка: `[[Артимед]]`
- **Глава** — `П<номер повести>.<номер главы> <Название>.md` → `П1.07 Воришки.md`, `П3.08 Покер.md`. Пролог = `.00`
- **Локация** — существительное: `Спортзал.md`, `Библиотека.md`, `Подвал.md`
- **Механика** — назывное: `Нормализация.md`, `Свет.md`, `Время и звонки.md`
- **Предмет** — единственное число: `Ботинок.md`, `Творожок.md`, `Вауцелюгель.md`

Имена файлов уникальны на всё хранилище — это позволяет короткие ссылки `[[Имя]]` без путей.

## 3. Свойства (frontmatter)

Ключ `tags` — латиницей (иначе не работает панель тегов). Остальные ключи по-русски.

### Персонаж
```yaml
---
тип: персонаж
канон: да            # да | нет (нет = придуман для игры)
фракция: учащиеся     # учащиеся | хулиганы | учителя | подвал | бомжи | вне фракций
глагол: уходит        # одно навязчивое свойство, см. §6
появляется:
  - Повесть 1
нормализуется: день 4 # день N | никогда | уже нормализован | не применимо
tags:
  - персонаж
---
```

### Глава
```yaml
---
тип: глава
повесть: 1
глава: 7
название: Воришки
строки-источника: 172-217
tags:
  - канон
---
```

### Локация / Механика / Предмет
```yaml
---
тип: локация        # локация | механика | предмет
этаж: первый        # только для локаций
фракция: хулиганы   # кто контролирует, если применимо
tags:
  - мир
---
```

## 4. Обязательные ссылки

- Каждое упоминание персонажа — `[[Имя]]`, при первом вхождении в заметке минимум.
- Каждая заметка главы линкует всех участвующих персонажей, все локации и весь важный реквизит.
- Каждая заметка персонажа линкует главы, где он появляется.
- Ссылка на несуществующую заметку допустима, если заметка **должна** появиться. Если не должна — не ссылаться.

## 5. Цитаты

Цитата из повести — блок `>` с указанием главы:

```
> «ДА ЭТО НЕ ШКОЛА!»
> — [[П1.03 Первый друг]]
```

Орфографию автора не исправлять: «естъ», «денъ», «малъчик». См. [[Орфография как хронология]].

## 6. Один глагол на персонажа

В повестях у персонажей нет психологии — есть одно навязчивое свойство, предъявляемое в любой ситуации. Это не бедность письма, а готовая механика NPC.

**Сохранять. Не углублять.** Персонаж, у которого появилась внутренняя жизнь, перестаёт быть жителем этого мира.

## 7. Callout-блоки

| Блок | Когда |
|---|---|
| `> [!danger] Канон — ломать нельзя` | факт, на котором висит логика мира |
| `> [!note] Решение` | принятое решение по игре |
| `> [!question] Предложение` | не утверждено |
| `> [!warning] Противоречие` | источник противоречит сам себе → в [[Противоречия канона]] |
| `> [!quote]` | голос персонажа |

## 9. Устаревшие производственные документы

Производственная ветка содержит только действующие решения. Документ, от которого решено отказаться полностью, удаляется вместе со ссылками и пересказами; база знаний не обязана хранить его как предмет обсуждения. История файлов принадлежит системе контроля версий, а не живому графу Obsidian.

Вернувшаяся идея записывается заново и обосновывается текущими потребностями игры. На удалённый документ нельзя ссылаться как на авторитет или отрицательный ориентир.

## 10. Граница между замыслом и реализацией

Разделы `01`–`07` описывают **что должна представлять и ощущать игра**. Они не фиксируют параметры движка, числовой баланс и структуру классов.

Раздел `08 Производство` описывает **как действующая технология создаёт этот замысел**: архитектуру, импорт графики, риги, инструменты и проверяемые этапы. Рабочие числа реализации хранятся в проекте Unity и профилях баланса; в Obsidian попадают только те ограничения, без которых невозможно принять производственное решение.

Механическая заметка может ссылаться на [[Производство]], но остаётся понятной без технического документа. Производственная заметка обязана ссылаться на ощущение или механику, которую она обслуживает.
